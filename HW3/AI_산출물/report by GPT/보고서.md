# 자료구조 Home Work #3 보고서

- 과목: 자료구조
- 작성 보조 AI: GPT-5.5 Codex

본 과제는 insertion sort, selection sort, heap sort, merge sort, quick sort를 직접 구현하고 Python built-in `list.sort()`와 실행 시간을 비교하는 것을 목표로 한다.

---

## 1. 해답

### 구현 요약

| 정렬 | 구현 방식 | 평균 시간복잡도 | 최악 시간복잡도 | 추가 공간 |
| --- | --- | --- | --- | --- |
| selection sort | 매 위치마다 남은 구간의 최솟값을 찾아 교환 | O(n^2) | O(n^2) | O(1) |
| heap sort | in-place max heap 구성 후 루트와 끝 원소를 교환하며 `sift_down` | O(n log n) | O(n log n) | O(1) |
| insertion sort | 앞쪽 정렬 구간에 현재 값을 삽입 | O(n^2) | O(n^2) | O(1) |
| quick sort | Lomuto partition, 마지막 원소 pivot, 재귀 in-place 정렬 | O(n log n) | O(n^2) | O(log n) 평균 재귀 스택 |
| merge sort | top-down 재귀 분할, 보조 배열 `aux`로 병합 후 원본 list에 복사 | O(n log n) | O(n log n) | O(n) |
| python sort | Python `list.sort()` 사용 | O(n log n) | O(n log n) | 구현 내부 공간 |

모든 정렬 함수는 입력 list를 직접 정렬하고 같은 list를 반환하도록 통일하였다. `merge_sort`도 보조 배열을 사용하지만, 함수 호출 후 입력 list 자체가 정렬된 상태가 되도록 구현하였다.

### 측정 프로토콜

- 데이터 파일은 `test1.dat`부터 `test5.dat`까지 순서대로 읽었다.
- 각 줄은 정수 1개로 보고 `int`로 변환하였다.
- `numpy` 사용 조건을 만족하기 위해 읽은 정수를 `np.array(..., dtype=np.int64)`로 변환한 뒤 list로 바꾸어 정렬 입력으로 사용하였다.
- 각 dataset마다 `expected = sorted(original)`을 한 번 생성하였다.
- 각 알고리즘은 원본 데이터의 fresh copy를 받아 정렬하였다.
- 시간 측정은 `time.perf_counter()`로 정렬 함수 실행 부분만 측정하였다.
- 파일 I/O, 정수 변환, fresh copy 생성, `assert` 검증은 타이머 밖에 두었다.
- 각 셀은 1회 측정값이다.
- 5개 dataset x 6개 알고리즘 = 30개 셀 모두 `assert result == expected`와 `assert data == expected`로 검증하였다.

## 4. 결과 분석

실측 결과는 O(n^2) 정렬과 O(n log n) 정렬의 차이를 분명하게 보여준다. 10K에서 100K로 데이터가 10배 증가했을 때 selection sort는 966.78ms에서 105012.14ms로 약 108.62배 증가했고, insertion sort는 1230.76ms에서 155797.97ms로 약 126.59배 증가했다. 반면 heap sort는 약 15.52배, quick sort는 약 13.38배, merge sort는 약 12.59배 증가하여 O(n log n)에 가까운 성장률을 보였다.

100K 기준으로 selection sort는 105012.14ms, insertion sort는 155797.97ms가 걸렸다. 같은 100K에서 quick sort는 87.08ms였으므로 selection sort는 quick sort보다 약 1205.93배, insertion sort는 약 1789.14배 느렸다. 입력 크기가 커질수록 O(n^2) 알고리즘은 비교 횟수가 급격히 늘어나기 때문에 큰 dataset에서는 실용성이 떨어진다.

Python built-in sort는 100K에서 9.77ms로 가장 빨랐다. quick sort와 비교해도 약 8.91배 빠르고, merge sort보다 약 14.64배, heap sort보다 약 18.81배 빠르다. Python의 built-in sort는 Timsort를 사용하며 C 수준으로 최적화된 구현이기 때문에, 같은 O(n log n) 계열이라도 상수항과 구현 최적화에서 큰 이점이 있다.

직접 구현한 O(n log n) 정렬끼리 비교하면 100K에서 quick sort가 87.08ms로 가장 빨랐고, merge sort가 143.06ms, heap sort가 183.76ms 순서였다. 이 실행에서는 quick sort가 merge sort보다 약 1.64배, heap sort보다 약 2.11배 빨랐다. merge sort는 보조 배열 복사 비용이 있고, heap sort는 heap 조정 과정의 비교와 교환이 많아 Python list 위에서는 quick sort보다 느리게 측정된 것으로 볼 수 있다.

## 5. 검증

각 dataset마다 Python `sorted(original)`로 기준 정답을 만들었다. 이후 6개 정렬 함수의 결과를 모두 기준 정답과 비교하였다.

- `assert result == expected`
- `assert data == expected`

총 30개 측정 셀에서 assert 검증이 모두 통과했으므로, 출력된 시간은 정렬 결과가 올바른 경우에만 기록된 값이다.

## 6. 출제 의도 (GPT-5.5 Codex 해석)

- 작은 입력에서는 정렬 알고리즘 간 차이가 작아 보이지만, 100K 입력에서는 O(n^2) 정렬과 O(n log n) 정렬의 실행 시간 차이를 직접 체감하게 하는 의도이다.
- 같은 O(n log n) 정렬이라도 quick, merge, heap, Python built-in sort처럼 구현 방식과 구현 언어에 따라 상수항 차이가 크게 날 수 있음을 비교하게 한다.
- 파일 I/O나 데이터 복사 시간이 섞이지 않도록 정렬 함수만 측정하고, 같은 원본에서 fresh copy를 만들어 공정하게 비교하는 방법론을 경험하게 한다.

## 7. AI (GPT-5.5 Codex) 사용 소감

GPT-5.5 Codex는 여러 정렬 알고리즘의 구현 조건과 측정 조건을 한 번에 맞추는 데 도움이 되었다. 특히 결과 검증을 `assert`로 넣어 시간 비교표가 잘못 정렬된 결과를 기준으로 작성되지 않게 한 점이 유용했다.
