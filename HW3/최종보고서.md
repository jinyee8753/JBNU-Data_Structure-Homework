### 측정 프로토콜 (두 AI 토의 합의안)

1. 알고리즘마다 원본 list 의 **fresh copy** 를 정렬한다 — 정렬된 입력을 재사용하면 insertion sort 가 O(n) 으로 왜곡된다.
2. `time.perf_counter()` 로 **정렬 함수 실행만** 측정한다 — 파일 I/O, int 변환, copy 생성, 정확성 assert 는 모두 타이머 밖.
3. 셀당 1회 측정 — 100K O(n²) 측정이 2분대라 반복 평균은 비현실적이며, 과제 목적은 알고리즘 간 상대 비교다.
4. 모든 결과를 `expected = sorted(원본)` 과 assert 비교 — 6 알고리즘 × 5 dataset = 30셀 전수 검증.
5. numpy 사용처: 데이터 int64 변환 (`np.array(..., dtype=np.int64)`), 결과 배열 처리. numpy 에는 직접 타이머 API 가 없어 시간 측정 자체는 표준 `time.perf_counter` 를 사용했다.

### "(In-place)" 해석

문법상 `(In-place)` 는 quick sort 에 대한 수식으로 해석했다. insertion / selection / heap 은 본질적으로 in-place 이며, merge sort 는 표준 보조 배열 방식으로 구현하되 호출 후 입력 list 자체가 정렬 상태가 되도록 부작용 계약을 유지했다. quick sort 는 in-place Lomuto partition 으로 구현했다.

## 1. 해답 — 구현 요약

| 함수 | 방식 | 시간복잡도 | 공간 |
| --- | --- | --- | --- |
| `insertion_sort` | key 를 왼쪽 정렬 구간에 삽입 (원소 우측 이동) | 평균/최악 O(n²), 최선 O(n) | in-place |
| `selection_sort` | 미정렬 구간 최솟값을 찾아 맨 앞과 교환 | 항상 O(n²) | in-place |
| `heap_sort` | bottom-up build-heap (max-heap) + sift-down | O(n log n) | in-place |
| `merge_sort` | top-down 분할 + 보조 배열 병합, 입력 list 에 재기록 | O(n log n) | O(n) 보조 |
| `quick_sort` | Lomuto partition, 마지막 원소 pivot | 평균 O(n log n), 최악 O(n²) | in-place |
| `built_in_sort` | `list.sort()` — Timsort (C 구현) | O(n log n) | O(n) 보조 |

- guide code 골격 (함수 6개 + `data_files` 루프 + `open("./{0}".format(f))` / `readlines` / `close`) 을 유지하고 TODO 만 채웠다.
- 강의 (06주차) 는 min-heap 기반 PQ-sort 개념을 다뤘으나, 오름차순 **in-place** heap sort 의 표준 구현은 max-heap 이므로 max-heap sift-down 을 사용했다.

## 2. 핵심 기능 요약

- **insertion sort** — 두 번째 원소부터 왼쪽의 정렬된 부분 배열에 key 를 끼워 넣는다. 이미 정렬된 입력엔 O(n). stable.
- **selection sort** — 비교 횟수가 입력과 무관하게 항상 n(n−1)/2. 교환 횟수는 최대 n−1 로 적다. unstable.
- **heap sort** — 배열을 max-heap 으로 만든 뒤 (O(n)), 루트(최댓값)를 배열 끝과 교환하고 힙 크기를 줄이며 sift-down 을 반복. O(n log n) 보장. unstable.
- **merge sort** — 반으로 분할해 각각 정렬 후 병합. O(n log n) 보장. stable. 병합에 보조 배열 필요.
- **quick sort** — pivot 기준으로 작은 원소를 왼쪽에 모으는 in-place partition 후 양쪽을 재귀 정렬. 평균 O(n log n), 최악(정렬/역정렬 입력) O(n²). 본 dataset 은 무작위라 평균 케이스.
- **python built-in sort** — Timsort (merge + insertion 하이브리드, C 구현). 부분 정렬 구간(run) 을 활용하는 적응형 정렬.

## 3. 출제 의도

- O(n²) 와 O(n log n) 의 점근적 차이를 **실측으로 체감** — 100K 에서 수백~수천 배 격차.
- 같은 O(n log n) 이라도 상수항·메모리 접근 패턴·구현 언어 (C vs Python 인터프리터) 에 따라 실측이 달라짐을 인식.
- in-place 개념과 partition / sift-down / merge 의 메모리 사용 차이 이해.
- 측정 방법론 (fresh copy, 측정 범위 격리) 과 numpy 도구 사용 경험.

### 6-2. 구현·표현 차이

- **코드 구조**: Claude 는 guide code 처럼 측정 루프를 모듈 최상위에 배치, GPT 는 `read_data`/`measure_sort`/`main()` 함수로 분리하고 `if __name__ == "__main__"` 가드를 사용.
- **quick sort 재귀 전략**: Claude 는 작은 쪽 먼저 재귀 + 큰 쪽 루프 처리 (재귀 깊이 ≤ log₂n 보장), GPT 는 단순 양쪽 재귀 + `sys.setrecursionlimit(300000)` 상향. 무작위 데이터에서는 둘 다 안전하다.

- **공통점**: Lomuto partition, max-heap sift-down, 보조 배열 merge, fresh copy 측정, sorted() assert 검증, np.int64 변환 — 합의 사양 전 항목 일치.

## 7. 통합 결과 분석

### 7-1. O(n²) 성장률 검증

- n 2배 (500→1K): selection 4.2배, insertion 4.5배 — 이론값 4배와 부합.
- n 10배 (10K→100K): selection 107배, insertion 116배 — 이론값 100배와 부합.

### 7-2. insertion vs selection

100K 에서 insertion (151.7초) 이 selection (104.7초) 보다 약 1.45배 느리다. selection 은 비교 위주 (교환 최대 n−1회) 인 반면, insertion 은 무작위 입력에서 평균 n²/4 회의 원소 이동 (리스트 쓰기) 을 수행하므로 인터프리터의 쓰기 연산 비용이 더해진 결과다. (단, 이미 정렬에 가까운 입력이라면 insertion 이 역전한다 — 적응성 차이.)

### 7-3. O(n log n) 3종 비교

100K 기준 quick (92.7ms) < merge (147.7ms) < heap (200.4ms).

- quick: partition 의 단일 순차 루프 — 캐시 친화적, 원소 이동량 적음.
- merge: 보조 배열 복사 오버헤드.
- heap: sift-down 의 비순차 (부모→자식 점프) 메모리 접근과 비교 횟수.

### 7-4. built-in (Timsort) 의 격차

python `list.sort()` 는 100K 에서 9.51ms — 같은 O(n log n) 인 quick 보다 약 10배, O(n²) 인 selection 보다 약 11,000배 빠르다. 동일한 점근 복잡도라도 C 구현과 Python 인터프리터 루프의 상수항 차이가 압도적임을 보여준다.

### 7-5. 통합 결론

- 점근 복잡도 (Big-O) 는 n 이 커질수록 지배적이다: 100K 에서 O(n²) 와 O(n log n) 의 격차는 500~1,600배.
- 같은 복잡도 안에서는 메모리 접근 패턴과 구현 언어가 실측을 결정한다: quick vs heap 2.2배, Python 구현 vs C Timsort 10배.
- 독립 구현 2종의 교차 검증 (100K 기준 ±10% 이내 및 100K 기준 순위 일치, 전체 입력 크기에서 점근 경향 일치) 과 30셀 sorted() assert 전수 검증으로 결과의 정확성을 확인했다.

## 8. 개인적인 사용 소감

이번에도 tmux 멀티 에이전트 환경에서 AI 들이 서로 토의하며 과제를 진행하는 방식을 사용했다. 구현에 들어가기 전에 과제 문장의 모호한 부분 — "(In-place)" 가 어디까지 걸리는지, numpy 로 시간을 재라는 요구를 어떻게 충족할지, 100,000개 데이터에 O(n²) 정렬을 정말 돌릴지 — 을 AI 둘이 항목별로 따져서 합의안을 만든 뒤에 코딩을 시작하니, 구현 단계에서 망설임 없이 진행되는 점이 좋았다.

특히 측정 방법론에서 "정렬된 배열을 재사용하면 insertion sort 가 O(n) 으로 왜곡된다", "copy 와 I/O 시간은 타이머 밖으로 빼야 built-in 과 공정 비교가 된다" 같은 디테일을 토의 과정에서 잡아낸 것이 인상적이었다. 결과적으로 독립 구현 2종의 100K 기준 측정값이 ±10% 이내로 일치했고, 소형 입력의 측정 노이즈에도 전체 점근 경향이 재현되어, 토의로 만든 사양의 재현성을 수치로 확인할 수 있었다.
